## 0. Endorsement schema stub — on `profile-consumption`, before merge

*Revised 2026-09-14: cut to a minimal slice. Everything removed is tracked in #288.*

Bear's rule is a **marker** rule, which needs only the cheap half of the endorsement design. The
graph/web-of-trust half stays out of this week entirely and lands after cutover, safely, because
`sources: []` means it never executes for anyone who has not opted in. This section is schema and
plumbing only: nothing enforces anything yet.

### 0a. Schema — exactly one new key

- [ ] `policies.access.endorsement` gains **one** property this week: `sources`, an ordered array of
      strings, default `[]`:

      "endorsement": {
        "type": "object",
        "additionalProperties": false,
        "properties": {
          "sources": {
            "type": "array",
            "default": [],
            "items": { "type": "string" }
          }
        }
      }

- [ ] `sources` entries are plain strings only — **no** object form, no `oneOf`. Each names an injected
      endorser (§2a). Order is significant: tried in sequence, first admit wins. The description should
      note that `graph` is reserved as a future built-in source name
- [ ] `sources: []` = stage OFF, so every existing profile, `octothorpes.json` included, behaves exactly
      as today. Purely additive, no migration
- [ ] `sources` filters **and** orders the injected endorser array — an injected endorser not named in
      `sources` never runs
- [ ] **NOT added:** `depth`, `record`, `autoRegister`, the `if`/`then` coupling between them, and
      `api.endorsers.available`. The first four are deferred to #288; `available` is a permanent
      non-goal, not a deferral
- [ ] `closed` becomes strictly whitelist-only — no registration, no endorsement. Update the
      `registration` enum description accordingly
- [ ] Coherence warnings (warn, never throw), two only: `sources` non-empty under `open` or `closed`
      (inert); a name in `sources` with no matching injected endorser (unresolvable, never admits)

*Verify:* ajv accepts `{}`, `{ "sources": [] }` and `{ "sources": ["bear-marker"] }`, and rejects an
unknown property under `endorsement`. Both coherence warnings fire without throwing.

### 0b. `createClient` accepts `endorsers`

- [ ] `createClient({ profile, endorsers: [ ... ] })` accepts and stores an array of `{ name, endorse }`
      and **does nothing with it yet**. The gate that consumes it lands in §2
- [ ] Both coherence warnings from 0a are implemented in the profile loader

*Verify:* a client constructed with no `endorsers` key behaves exactly as today; a client constructed
with endorsers behaves exactly as today. Both coherence warnings fire without throwing.

### 1b. Follow-up: extract built-in harmonizers to flat files

Immediate follow-up to approving the profile — **it may change profile structure**, so it wants to
land close behind rather than drift.

Today built-in harmonizers are inline JS objects in `packages/core/harmonizers.js` while site
harmonizers are JSON in `api.harmonizers.dir`. They do not share a signature, and
`harmonizerRegistry.register()` **warns and skips** on a name collision — so overriding a builtin is
not merely awkward, it is impossible.

- [ ] Decide the interpolation convention: the builtin `default` embeds the instance
      (`` `link[rel='preload'][href*='${instance}']` ``), so flat JSON needs either a token
      (`{{instance}}`) resolved at registry build, or instance-relative selectors that need no
      substitution
- [ ] Decide the override semantics: last-wins, or explicit (`"extends": "default"`)? Silent last-wins
      on a builtin name is a footgun
- [ ] **Open: does this need a new profile slot for default overrides?** Answer before the profile
      shape is treated as settled
- [ ] Extract builtins to flat files once both are decided

Related: #287 (a single harmonizer schema would then cover builtins and site harmonizers alike).

## 2. Endorsement gate + `bear-marker` — on `development`, after merge

This is a **feature merge into `development`** and must land before `merge-prep` is cut.

### 2a. Endorser injection

- [ ] Endorsers are **injected, not discovered**. `createClient` already accepts the array (§0b); this is
      the contract it must satisfy. Same pattern as the existing injected `verifyOrigin` dep
- [ ] Core does **no** directory walking, no `static/endorsers/`, no basename keying. Core knows nothing
      about client directory structure
- [ ] Where the adapter in this repo keeps its Bear module (under `src/lib`, under `static/`, anywhere)
      is adapter business — it imports it and passes it in
- [ ] Contract: `endorse({ origin, blobject, content, contentType }) -> boolean`. Return `true` to admit;
      **anything else declines**. No three-valued `undefined`/`false` distinction
- [ ] `content` (raw body) is passed as well as `blobject` — **required**: Bear's marker is a bare
      `<meta content='…'>` with no `name`, so no harmonizer selector extracts it and it is absent from
      the blobject. Both are already in hand at the gate, so passing both costs nothing

*Verify:* an injected endorser named in `sources` is reached, one not named in `sources` is not.

### 2b. Gate stage 4

- [ ] Insert endorsement in `checkAccessGate` (`packages/core/access.js`), between the registration check
      and the default deny
- [ ] Runs **only** when registration fails, and **only** under `registration: 'registered'`.
      `closed` stays strictly whitelist-only
- [ ] Sources tried in `sources` order, first `true` admits
- [ ] Evaluated **per request**. Nothing is stored — phrase it in terms of the origin, but do not claim
      admission persists at origin level
- [ ] **Semantic change from `main`, state it in the code comment:** `main` checks the marker on the
      origin's root page via a separate fetch; this gate checks the page that requested indexing, which
      was already fetched and harmonized before the gate. Bear puts the marker on every page, so the
      outcome matches, but the check is no longer origin-root

*Verify:* an unregistered origin with no matching endorser still hits the default deny; `open` and
`closed` profiles never reach stage 4.

## 3. #285 — term IRI encoding, on both branches

The `~/` crash: a term containing a space produces an invalid SPARQL IRI → 500. Separate
implementations per branch; the call-site layouts differ, so this is not a cherry-pick.

- [ ] **`main`**: `termIri(instance, name)` helper, applied at ~28 sites across 11 files
      (`packages/core` *and* `src/lib` duplication, plus `src/lib/assert.js` and
      `src/routes/~/[thorpe]/{load.js,rss/+server.js}`)
- [ ] **`main`**: deploy and confirm against the reporting page on #279
- [ ] **`development`**: same helper, 18 sites across 4 files
      (`packages/core/{indexer,queryBuilders,api}.js`, `ld/rdfa2triples.js`)

Constraints, both branches:

- Encode once at IRI construction. **No decode/re-encode round-trip** — `decodeURIComponent` throws
  `URIError` on a term like `100%`.
- Read side matters as much as write side: `/get` params arrive URL-decoded, so a term written encoded
  but queried raw is unreachable.
- Encoding is **not** normalization. Leave `getFuzzyTags` alone.

Tests: `termIri()` unit coverage (space, `%`, `>`, `"`, `{`, `}`, non-ASCII, already-encoded input);
a regression indexing a doc whose harmonizer yields a spaced hashtag; a parity assertion that the
RDFa `<a href>` path and the harmonizer textContent path produce the **same** IRI.

This is intended as the **last hotfix to `main` before cutover**.
