## Hand-test guide (local, dev server + store on :7879)

Re-index / reconcile (#267):
1. Index a devdemo page twice; second run should log no writes — verify with `reindexReconcile` semantics: timestamps unchanged, no new triples.
2. Edit a page's markup: drop a tag, change a subtype (bookmark → cite), re-index; old statement gone, new one present, unrelated statements untouched.
3. Re-index a page with a pending alias: warning still returned, no churn.

Batch endpoint (#180):
1. `curl -X POST {instance}index/batch -H "Origin: {instance}" -H "Content-Type: application/json" -d '{"urls": ["<devdemo url 1>", "<devdemo url 2>"]}'` → 200, per-item results + summary.
2. Same without Origin header → 400. Blobjects-only without Origin → processed (anchor-token path; expect 403 unless submissions enabled in profile).
3. 101+ items → whole-set 400 (`policies.indexing.maxBatchSize`, default 100).
4. Repeat a batch inside the cooldown window → items come back `skipped`, not errors, and the whole batch charges each origin's rate bucket once.
5. Partial-blobject safety: submit a stripped blobject with `"reconcile": false` → nothing deleted; same submission without the flag → missing statements retracted. The "a blobject represents the whole document" contract is the thing under test.

Sitemap recipe (#177):
1. Parse-only pass of any real sitemap through the `sitemap` harmonizer (orchestra-pit or `batchHarmonize` return-only), lift `octothorpes[].uri`, POST as `urls`.
2. Never write-ingest the sitemap blobject itself — if it shows up as a subject in the store, that's the bug.

createClient migration smoke (should all be byte-identical to before):
- `GET {instance}index` no uri → 400; `POST {instance}index` no Origin → 400; cross-origin header → 403; blobject submission with submissions off → 403; `/get/...` routes → 200.
