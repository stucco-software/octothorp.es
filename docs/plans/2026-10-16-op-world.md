# OP World

- Date: 2026-10-16
- Status: design, agreed in session 2026-10-16, v0.8 candidate — assumes v0.7 shipped (RDF-star #270, Deletion #271, Batch Indexing #274, vocabulary epic #316)
- Relates to: #217 (federation/changefeed context); #321 (registration requests); #291 (vocab doc); #192 (content labels); harvest/ingest design `docs/plans/point7/2026-10-15-harvest-ingest.md`

## Conclusions

- OP World (world.octothorp.es) is a relay-of-relays: a stock OP relay whose registered "sites" are other relays. It serves blended feeds and network-wide browse.
- Every layer reuses existing machinery at a different granularity. The only new endpoint is `/changefeed`.
- World stores core statements only. documentRecord (DR) data is never stored; the UI loads it from the source relay at render time.
- Moderation has three tiers: World-level, member-propagated, viewer-level. Blended label display is most-restrictive-wins.
- Membership is defined by a conformance profile over the existing `profile.schema.json`, not by new schema fields.

## 1. Architecture

1. Identity/admission: a relay registers by its profile card. Admission is the #321 requested→verified lifecycle with relays as the unit. The admin previews via the profile card plus a harvest of the relay's recent feed. The conformance check (section 4) runs mechanically at admission and records pass/fail on the request.
2. Changefeed: `/changefeed` returns cursor-paginated statements since a cursor. It MUST carry retractions (Deletion, v0.7) so World tracks member deletes and bans. Members may exclude documentRecord statements from the feed (section 2).
3. Sync worker: cron harvest of each member's changefeed cursor → `ingest()`, with `octo:source <relay>` on every statement via RDF-star statement metadata. A slow-cycle profile re-fetch catches declaration changes and dead relays.
4. Blended feeds: the existing `/get` API over the merged store, plus a `source=` route facet.
   - Page collision is intended: the same URL from two relays merges onto one node by identity, with per-relay provenance per statement. Backlinks aggregate across the network with no extra work.
   - Display needs a dedupe-by-source rule.
5. One-hop rule: World never ingests statements whose `octo:source` is another aggregator. No aggregator loops, no double-counting. Same no-recursion law as harvest.
6. Term unification deferred: v1 blending groups terms by `skos:prefLabel` string match across relays. Hub IRIs / `skos:exactMatch` ship only when label grouping visibly fails.

## 2. documentRecord: dynamic, never stored (maintainer ruling)

- World stores core statements only. DR data loads in the UI from the source relay:
  - provenance names the relay to ask;
  - that relay's profile + generated vocab doc (#291) name the DR fields and their ranges (render hints);
  - the fetch is the source's existing `/get?s=<page>` blobject.
- Why: matches the triplestore philosophy (network facts, not copies); DR cannot go stale or collide; deletion authority stays at the source; changefeeds shrink.
- This removes projection composition and range conflicts. World never merges two relays' `octo:wordCount`; it renders each relay's DR under that relay's own schema.
- Requirements created:
  - CORS on members' `/get` (membership requirement).
  - Graceful degradation: source down → core card renders from World, DR panel shows unavailable. Feeds never block on member uptime.
- The rendering widget is the harvest doc's publisher-template component pattern, pointed at the source relay.

## 3. Moderation

1. World-level: relay-granular wholesale drop via provenance, plus ordinary page/domain bans (exists).
2. Member-propagated: changefeed retractions carry member deletions/bans. World follows the source by default.
3. Viewer-level: content labels (#192, statement metadata) become filter facets in blended feeds. This is the new UI work.
4. Label disagreement: most-restrictive-wins in blended display, with the label's source attributed. World must not launder a member's warning away.

## 4. OP World conformance

`profile.schema.json` currently marks nothing required, so conformance is a profile over the schema. The conformance doc names the v0.7 API surface explicitly; surface changes mean a conformance rev, not silent breakage.

### Tier 1: profile card

- Required fields:
  - `identity.instance` — canonical base URL; must match the URL serving the profile. This is the admission key.
  - `identity.name`, `identity.description`
  - `identity.contact` — abuse reachability, non-negotiable.
  - `identity.terms`, `identity.rules`
  - `policies.indexing`, `policies.access`
- Conditionally required: `api.documentRecord` + `vocabulary.namespaces`, only if the relay wants DR panels rendered. Absent = core-only membership, valid.
- Shape: validates against the published, version-pinned `profile.schema.json` (card carries `$schema`) with zero errors. Coherence warnings are acceptable.

### Tier 2: API surface

1. `/profile.json` at instance root, matching the live relay.
2. `/get/[what]/[by]` with current params (`s`, `o`, `match`, `limit`, `offset`) and current blobject shape.
3. CORS on `/get` permitting World's origin.
4. `/changefeed` with cursor pagination and retractions.
5. Honest `octo:` vocabulary: canonical full IRIs per the v0.7 ruling, `skos:prefLabel` on terms. A relay running v0.7+ core conforms by construction.

## 5. Build sequence

1. `/changefeed` endpoint with retractions. The one real feature; also a data source for #270 migration verification.
2. World deploy (stock relay, aggregator-declaring profile) + relay admission (#321 reuse + mechanical conformance check).
3. Sync worker: cron harvest → ingest with source provenance; slow profile re-fetch.
4. Blended UX: `source=` facet, network browse, dynamic DR panels, label filter facets, dedupe-by-source display rule.
5. Hub-IRI term unification, only when prefLabel grouping breaks.

## Open questions
